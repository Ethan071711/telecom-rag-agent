# 运营商客服助手演示与讲解

这份说明按“用户问题、业务规则、代码处理、运行结果、局限”串起现有项目。先自己操作，再按实际掌握程度介绍。项目使用虚构的青禾通信资料；没有真实运营商客户或生产部署。

## 先跑起来

Windows PowerShell 中，已有依赖环境时执行：

```powershell
$env:LLM_PROVIDER = 'offline'
python run.py web
```

`offline` 使用规则路由和原文抽取，不调用付费大模型。检索仍使用本地的向量模型和重排模型；首次安装时需要下载这些模型。已缓存模型的机器可以另设 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1`，防止联网下载。

安装和其他后端的详细命令见仓库首页与 `TECHNICAL_NOTES.md`。不要把离线规则演示介绍成正在运行 Qwen 或云端模型。

## 三个演示问题

| 用户要做什么 | 输入 | 重点看什么 |
|---|---|---|
| 查一条办理规则 | 携号转网对在网时长有什么要求？ | 回答是否附资料引用；展开原文能否找到对应规则 |
| 算套餐费用 | 我用的是5G畅享39元套餐，这个月用了70GB流量、打了100分钟电话，要交多少钱？ | 是否调用 `calculate_fee`，参数和计算过程是否可查看 |
| 继续追问 | 青春校园卡每个月多少钱？随后问：那毕业以后会怎么样？ | 页面会展示补全后的检索问题；离线规则对复杂追问有局限，答错时如实展示 |

再试一次知识库没有的业务，例如“卫星电话怎么收费”。如果系统没有拒答，应记录这个失败，不能为了演示效果把它说成全部场景都能可靠拒答。

## 每个步骤为什么存在

**用户先问业务问题。** 服务条款在 `data/docs/`，套餐数值在 `data/plans.json`。先检查资料是不是虚构数据、规则是否完整，再看模型输出。

**所以先检索资料。** `telecom_rag/documents.py` 按标题和段落切块。`telecom_rag/retriever.py` 同时做向量与 BM25 检索，用 RRF 合并排序，再用重排模型选择片段。这样做是为了兼顾同义表达和具体业务词；不代表组合一定优于单种方法，需看评测。

**涉及计算时交给业务函数。** `telecom_rag/tools.py` 实现套餐查询、费用计算、推荐和知识再检索。模型或离线规则负责选择工具、填写参数；金额计算在普通 Python 函数中完成。

**最后把答案与依据一起展示。** `telecom_rag/agent.py` 管理检索、工具循环和引用映射。`telecom_rag/web.py` 展示回答、原文、工具参数及耗时，方便人检查回答依据。

**结果用自测记录检查。** `tests/` 检查程序行为；`eval/eval_set.jsonl` 是 49 条业务自测。二者不能混称为 87 个真实客户案例。自测与知识库同源、样本小，结果不能外推为线上准确率。

## 先学会解释这六个问题

1. `calculate_fee` 收到的套餐、流量、通话数分别从哪里来？改一个参数，金额如何变化？
2. BM25 和向量检索各返回什么，RRF 怎样合并它们？
3. 引用编号怎样映射到原文，引用到了资料是否就代表整句话一定正确？
4. 对话历史中的旧引用编号为什么要清除？
5. 规则基线和大模型后端分别做了什么，本次实际运行的是哪个？
6. 自测集怎样构造、怎样判分、有哪些已知失败？

这六个问题还解释不清时，简历使用“个人学习与复现项目”，不使用“独立完成架构设计、生产上线、性能调优”等表述。

## 可以做的一次真实修改

在虚构业务文档中修改一条规则，重建索引，再用原问题和一个换说法的问题检查变化。提交记录写清改了哪条资料、如何验证、是否影响费用工具。先做这一项小改动，不同时更换框架或增加多个 Agent。

如果业务规则同时影响文档与 `plans.json`，两处都要核对；只改文案可能导致检索回答与计算结果不一致。未经实际测试，不在简历中写“已解决”或填写提升比例。

## 面试时的介绍方式

先说明这是个人演示与学习项目，再根据真实情况说出自己的工作。例如：复现运行、梳理资料、阅读工具调用流程、修改业务规则、检查测试结果。代码使用了 AI 辅助时，可以直接说明工具怎样帮助自己、哪些部分仍不能独立完成。

介绍项目已有功能时用“项目支持”；介绍自己的贡献时用“我实际完成”。不要把第三方仓库的功能、旧实验数据或本轮由编码助手执行的工作，自动改写为自己过去独立完成的经历。
